# AIS normalizer fixture

`backend/app/feeds/ais.py` normalizes vessel rows from a self-hosted
[position-api](https://github.com/transparency-everywhere/position-api) instance (D-078).
`cases.json` here is asserted by `backend/tests/test_ais.py`.

Unlike `fixtures/adsb/`, there is currently **one** implementation of this normalizer, not two:
the single-file build has no position-api proxy and says so honestly instead of shipping a
browser-direct AIS path. If a second implementation ever appears, it must assert THIS file, the
same way the two ADS-B normalizers share `fixtures/adsb/cases.json` — that is the whole reason
the fixture lives outside `backend/`.

## Provenance — read this before trusting a case

**Every case in `cases.json` is `synthetic: true`.** There was no live position-api instance
reachable when this fixture was written, so no row here is a captured measurement. Each case is
constructed from position-api's own source code — the `mapResult` mapping in `src/legacy/area.ts`
names the exact output fields (`name`, `id`, `lat`, `lon`, `timestamp`, `mmsi`, `imo`,
`callsign`, `speed`, `area`, `type`, `country`, `destination`, `port_current`, `port_next`) and
the JS `Number(...)` coercions that can leak `null` (from `NaN`) into them.

That distinction is recorded per-case so nobody later mistakes a constructed record for a
measurement — the same reason CLAUDE.md ground rule 1 exists. **The first thing to do once a
live instance is running is capture real rows** (`GET /legacy/getVesselsNearMe/...` verbatim),
store them here as `raw-position-api.json`, and promote real records into `cases.json` —
exactly what `fixtures/adsb/` did with its three feeds. The speed unit (assumed knots, see
`docs/data-sources.md` §5.1c) must be verified at the same time.

`expected` was generated by `ais.py` and then checked by hand against position-api's mapping,
case by case, before being committed. If a test goes red, the question is "which side is
wrong", not "how do I refresh the fixture".
